1. Business Overview & Problem Statement

Why this feature was built and what business goals it accomplishes.

Executive Summary

Previously, every new user signup immediately created an ACTIVE user and hostel workspace, granting immediate access to all hostel management tools (bed allocations, KYC documents, financial invoicing, POS amenities) without requiring payment confirmation.

The Solution: The Hybrid Gated Onboarding system introduces a zero-trust commercial barrier:

  • Immediate Account Isolation: Newly registered users and hostels are assigned status INACTIVE.
  • Zero-Distraction Payment: Inactive owners are routed to a dedicated, high-conversion payment page with UPI QR and selected plan pricing.
  • No Receipt Uploads / No WhatsApp Bottlenecks: Owners enter their 12-digit UTR (UPI Transaction Reference number) directly into the app.
  • Instant Admin Reconciliation: Administrators cross-reference the 12-digit UTR with bank deposits and activate the account with a single SQL query or admin action.
  • Auto-Unlock: The user's screen polls in the background every 15 seconds; the moment approval occurs, the dashboard unlocks automatically without re-login.

2. User Lifecycle & State Machine

The progression of user status from signup to full workspace access.

1

Registration Phase (Signup)

Hostel owner signs up via /signup. Backend creates User (status = INACTIVE) and Hostel (status = INACTIVE). Issues authenticated JWT token.

2

Gated Onboarding (Activation Pending)

React routes owner to /activation-pending. User sees dynamic UPI QR code for their selected plan and a 12-digit UTR input form. All dashboard routes are blocked.

3

Proof Submission

Owner transfers funds in GPay/PhonePe/Paytm, copies 12-digit UTR, and clicks Submit UTR Reference. Backend persists record in subscription_requests with status PENDING.

4

Admin Verification & DB Activation

Super-Admin verifies ₹ credit in bank portal against submitted UTR number. Admin updates user and hostel to ACTIVE and subscription request to APPROVED.

5

Immediate Unlock & Dashboard Access

Owner clicks Check Status Now (or 15s auto-poller triggers). Backend returns UserStatus.ACTIVE. Frontend routes user to / (Dashboard). All APIs become available.

3. Backend Architecture & Components (Spring Boot)

Implementation details inside the aavas microservice.

Core Backend Classes & Responsibilities

Component Type File Location Responsibility
ActiveAccountFilter Spring Security Filter security/ActiveAccountFilter.java Intercepts every HTTP request. If user or hostel status is not ACTIVE, halts execution immediately with HTTP 403 Forbidden.
SecurityConfig Configuration config/SecurityConfig.java Registers ActiveAccountFilter in filter chain immediately after JwtAuthenticationFilter.
UserPrincipal Security Model models/UserPrincipal.java isEnabled() checks user.getStatus() != UserStatus.BLOCKED. Allows inactive users to login and maintain activation session.
AuthServiceImpl Service implementations/AuthServiceImpl.java On signup(), assigns UserStatus.INACTIVE and HostelStatus.INACTIVE.
SubscriptionRequest JPA Entity models/SubscriptionRequest.java Stores hostel_id, user_id, plan_name, amount, utr_number, status (PENDING, APPROVED, REJECTED).
SubscriptionController REST Controller controllers/SubscriptionController.java Exposes POST /api/v1/subscription/submit-utr and GET /api/v1/subscription/status.

4. Frontend UI & Routing Architecture (React)

Client-side protection, gated views, and state management in atithi.

2-Step Onboarding Architecture

A

SelectPlanRoute.tsx → /select-plan (Step 1 of 2)

When a newly registered owner signs up or logs in with status === "INACTIVE", they land on /select-plan.
• Displays all 3 subscription plans using the shared, high-conversion <PlanCard /> components.
• Features clean Activate CTA buttons (no FAQ distractions).
• Clicking Activate navigates to /activation-pending passing the selected plan ID.

B

ActivationPendingRoute.tsx → /activation-pending (Step 2 of 2)

Guards the payment and verification screen.
• Renders selected plan summary with a ← Change Plan button back to /select-plan.
• Shows dynamic UPI QR code, 1-click Copy UPI ID, and 12-digit UTR submission box.
• Includes 15-second silent background polling and manual Check Status Now action.

C

ProtectedRoute.tsx

Wraps all internal business views (/, /customers, /rooms, /payments, etc.).
• If !user → Redirects to /login.
• If user.status === "INACTIVE" → Redirects immediately to /select-plan.
• If user.status === "ACTIVE" → Renders internal dashboard layouts.

D

PublicRoute.tsx

Guards /login and /signup.
• If logged-in user has status === "INACTIVE" → Redirects to /select-plan.
• If logged-in user has status === "ACTIVE" → Redirects to /.

Component Reusability (src/data/plans.tsx & PlanCard.tsx)

Plans data is centralized in src/data/plans.tsx, ensuring single-source-of-truth pricing and features across the system. The cards are encapsulated inside PlanCard.tsx with configurable buttonText, allowing the same visual design to be used with "Activate" on /select-plan and "Upgrade" / "Extend Plan" on the internal /plans page.

Key Features of ActivationPending.tsx

  • 3-Tier Plan Selector: Quarterly Starter (₹10,499), Half-Yearly Pro (₹19,945), Annual Enterprise (₹35,689).
  • BHIM UPI QR Code: Displays the official BHIM UPI QR code (/QR_bhim.png) for instantaneous mobile scanning.
  • 1-Click Copy UPI ID: Copies 7997712658@upi to clipboard with instant confirmation feedback.
  • 12-Digit Strict UTR Input: Monospaced, uppercase formatted input that validates exact length and alphanumeric characters.
  • Submitted State Card: Shows the recorded UTR, selected plan, timestamp, and animated amber "Pending Verification" badge.
  • Edit/Update Support: Allows the user to fix typos by clicking "Update UTR".
  • Instant "Check Status Now" Button: Triggers immediate server refresh without noisy background polling loops.

5. Security Specification & Penetration Defense

Proof of security against common API exploitation vectors.

Direct API Bypass (Postman / Curl)

PREVENTED

Threat: An inactive user copies their valid JWT from browser storage and uses Postman to call GET /api/v1/customers.

Defense: ActiveAccountFilter runs on every HTTP request. It inspects the principal before dispatching to controllers and rejects with HTTP 403 Forbidden.

SQL Injection & Parameter Tampering

PREVENTED

Threat: Malicious input like ' OR 1=1-- passed via URL path, query params, or UTR JSON payload.

Defense: 1) JPA uses prepared statements exclusively. 2) UTR is strictly validated by @Pattern(regexp="^[0-9A-Za-z]{12}$"). 3) Blocked users never trigger business queries.

Cross-Site Scripting (XSS)

PREVENTED

Threat: Injecting <script>alert(1)</script> into UTR notes or payment fields.

Defense: Spring Boot returns pure JSON. React JSX escapes all rendered strings automatically. Input validation rejects non-alphanumeric UTR strings upfront.

Multi-Tenancy Isolation

PREVENTED

Threat: Inactive hostel user attempting to read another hostel's data.

Defense: Dual verification: both user.status === ACTIVE AND hostel.status === ACTIVE are enforced at the filter and controller layers.

7. Admin Operations Runbook & SQL Queries

Standard operating procedure for administrators to verify and activate accounts.

Step 1: Check Pending Payment Requests

Run this query to view all pending UTR numbers submitted by customers awaiting activation:

SELECT 
    sr.id AS request_id,
    u.email AS owner_email,
    u.name AS owner_name,
    h.name AS hostel_name,
    sr.plan_name,
    sr.amount,
    sr.utr_number,
    sr.created_at
FROM subscription_requests sr
JOIN users u ON sr.user_id = u.id
JOIN hostels h ON sr.hostel_id = h.id
WHERE sr.status = 'PENDING'
ORDER BY sr.created_at ASC;

Step 2: Reconcile in Bank / UPI App

Open your Business Bank / Google Pay / PhonePe merchant portal. Search for the utr_number (e.g. 428719827361). Confirm that the credit amount matches the plan price.

Step 3: Activate Account in Database

Once payment is confirmed, execute this single transactional SQL script:

-- 1. Activate the User
UPDATE users 
SET status = 'ACTIVE' 
WHERE email = 'customer@example.com';

-- 2. Activate the Hostel
UPDATE hostels 
SET status = 'ACTIVE' 
WHERE id = (SELECT hostel_id FROM users WHERE email = 'customer@example.com');

-- 3. Mark Subscription Request as APPROVED
UPDATE subscription_requests 
SET status = 'APPROVED' 
WHERE utr_number = '428719827361';
Instant Effect: No Server Restart Required

Because JwtAuthenticationFilter retrieves user state directly from the database upon every token verification, the user is active the exact millisecond this query commits. No token re-issue or session clearing is needed.
