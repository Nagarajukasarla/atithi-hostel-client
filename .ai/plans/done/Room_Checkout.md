## 1. Current State & Problem Analysis

### What happens currently:
1. In [`DailyRooms.tsx`](file:///d:/resource/Projects/Hostel%20Management/atithi/src/pages/DailyRooms.tsx#L916-L921), clicking the exit button opens a generic [`ConfirmDialog`](file:///d:/resource/Projects/Hostel%20Management/atithi/src/pages/DailyRooms.tsx#L1253-L1261).

## 2. Strategy: Handling Database Entities & Cancelling Unnecessary Charges

### Entity & Ledger Architecture:
- [`RoomAllocation`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/models/RoomAllocation.java): Tracks `checkInDate`, `checkOutDate`, and `status` (`ACTIVE`, `ENDED`).
- [`AllocationFinancialTerms`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/models/AllocationFinancialTerms.java): Stores `billingMode` (`DAILY`), `dailyRate`, and `securityDepositRequired`.
- [`Charge`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/models/Charge.java):
  - Each day is billed as a separate [`Charge`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/models/Charge.java) with `chargeType = ChargeType.DAILY_RENT`, `periodStart = date`, `periodEnd = date`, and `status = OPEN | PAID | PARTIAL | WAIVED`.
  - Unique constraint: `uk_charge_allocation_period` on `(allocation_id, charge_type, period_start)`.
- [`Payment`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/models/Payment.java) & [`PaymentAllocation`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/models/PaymentAllocation.java): Payments are allocated against open charges oldest-first.
- Outstanding balance is computed in [`ChargeServiceImpl.java`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/implementations/ChargeServiceImpl.java#L200-L205):
  $$\text{Outstanding Balance} = \sum(\text{Total Charges}) - \sum(\text{Total Paid Allocations})$$

### How to safely cancel/adjust unnecessary charges when checkout is backdated:
When the receptionist selects a `checkOutDate` that is **earlier than today** (e.g. guest left yesterday `2026-10-01`, but updated today `2026-10-02`):
1. **Ensure Complete Charges for the Active Period**:
   - For all dates from `checkInDate` to `checkOutDate`, verify that a `DAILY_RENT` charge exists. If the cron job hasn't run yet, generate any missing charges up to `checkOutDate`.
2. **Handle Charges Beyond the Checkout Date (`periodStart > checkOutDate`)**:
   - Query all charges linked to this allocation where `chargeType = DAILY_RENT` and `periodStart > checkOutDate`.
   - **Check for payments**: Since payments are allocated oldest-first, future/unnecessary charges almost never have payments allocated.
   - **Action**:
     - For any unallocated charges (`status = OPEN`), **delete them** from [`ChargeRepository`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/repositories/ChargeRepository.java)
     - *Why deletion of unallocated speculative daily charges is best:* The service was never rendered because the guest vacated earlier. Deleting unallocated charges restores the ledger cleanly so `sumTotalCharges` immediately reflects the exact charges for the stay duration without needing custom exception filters.
3. **Calculate Accurate Due for the Selected Date**:
   $$\text{Stay Days} = \max(1, (\text{checkOutDate} - \text{checkInDate} + 1))$$
   $$\text{Total Expected Tariff} = (\text{Stay Days} \times \text{dailyRate}) + \text{securityDeposit}$$
   $$\text{Remaining Due} = \max(0, \text{Total Expected Tariff} - \text{Total Paid})$$

2. **Add Checkout Preview Endpoint**:
   - `GET /api/v1/room-allocation/{id}/checkout-preview?checkOutDate=YYYY-MM-DD`

     - Create `Payment` entity with `paymentType = PaymentType.DAILY_RENT` and `paymentDate = checkOutDate`.
     - Allocate payment using [`paymentAllocationService.allocatePaymentAgainstOldestCharges(...)`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/implementations/PaymentAllocationServiceImpl.java#L33-L101).
   - Set `allocation.setCheckOutDate(checkOutDate)` and `allocation.setStatus(AllocationStatus.ENDED)`.
   - Update room occupancy count and room status (`VACANT` or `PARTIALLY_FILLED`).

### Phase 2: Frontend (`atithi`)
1. **Update API Services**:
   - In [`roomAllocationService.ts`](file:///d:/resource/Projects/Hostel%20Management/atithi/src/api/roomAllocationService.ts):
     - Add `getCheckoutPreview(allocationId, checkOutDate)`.
     - Update `endAllocation(allocationId, payload)` to pass `checkOutDate` and optional `payment`.
2. **Build the Interactive Checkout & Settlement Modal in `DailyRooms.tsx`**:
   - Replace the generic `ConfirmDialog` with the new integrated checkout modal.
   - Input date picker bounded between `checkInDate` and `todayStr`.
   - Real-time stay duration and due calculation.
   - Dynamic UI:
     - When `due > 0`: Display payment fields (Amount, Method, Notes) and the button **"Pay & Check-out"**.

## 1. Monthly Architecture & Current Problem Analysis

### Current State in `Customers.tsx` and Backend:
1. In [`Customers.tsx`](file:///d:/resource/Projects/Hostel%20Management/atithi/src/pages/Customers.tsx#L1009-L1021), active monthly residents display an **Exit** button in the Actions column.
2. Clicking **Exit** opens a standard [`ConfirmDialog`](file:///d:/resource/Projects/Hostel%20Management/atithi/src/pages/Customers.tsx#L1340-L1349):
   ```tsx
   title="End Customer Stay?"
   description="Are you sure you want to end the current stay for {name}? This will release the assigned room/bed and mark the allocation as ended. Existing charges and payment history will remain unchanged."
   ```
3. Clicking "End Stay" triggers `roomAllocationService.endAllocation(endStayTarget.allocationId)` which hits `POST /api/v1/room-allocation/{id}/end` with **no body**.
4. In [`RoomAllocationServiceImpl.java`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/implementations/RoomAllocationServiceImpl.java#L108-L138):
   - It sets `checkOutDate = LocalDate.now()`.
   - It sets `status = AllocationStatus.ENDED`.
   - It decrements room occupancy count.
   - **Critical Problem 1: No Mid-Cycle Pro-Ration**:
     If a resident checks in on Jan 1 with ₹6,000 monthly rent, and checks out on Feb 10, the daily cron job on Feb 1 already generated a full ₹6,000 charge for Feb 1 to Feb 28. If the resident vacates on Feb 10, the system leaves the full ₹6,000 charge on the ledger. The customer is unfairly burdened with 18 days of unused rent (Feb 11 to Feb 28)!
   - **Critical Problem 2: Excess Days Unbilled**:
     If a resident's cycle ended on Jan 31, and checkout is Feb 5, but the cron hasn't run yet or the anchor date delayed charge creation, the resident leaves without paying for the 5 days stayed in February.
   - **Critical Problem 3: Security Deposit Is Completely Ignored**:
     Monthly residents pay a mandatory Security Deposit at registration (e.g. ₹5,000). At checkout, this deposit must be reconciled:
     - Damages / maintenance penalties deducted.
     - Unpaid pro-rated rent adjusted against the deposit.
     - Net remaining deposit refunded to the resident.
     Currently, there is no refund or deposit deduction mechanism at all!
   - **Critical Problem 4: Zero Due Clearance Guard**:
     A monthly resident with thousands of rupees in unpaid dues can be checked out and vacated with a single click in `ConfirmDialog` without collecting payment.

## 2. Monthly Rent Pro-Ration & Financial Calculation Rules

### The Billing Cycle Model:
Monthly residents have a `billingAnchorDate` in [`AllocationFinancialTerms`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/models/AllocationFinancialTerms.java) (defaults to `checkInDate`).
- **Initial Cycle (Cycle 0)**: Created at registration by [`CustomerStayServiceImpl`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/implementations/CustomerStayServiceImpl.java#L193-L203):
  $$\text{Period 0} = [\text{checkInDate},\, \text{checkInDate.plusMonths(1).minusDays(1)}]$$
- **Subsequent Cycles (Cycle $k \ge 1$)**: Generated by [`RentChargeServiceImpl`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/implementations/RentChargeServiceImpl.java#L74-L75):
  $$\text{Period } k = [\text{anchor.plusMonths}(k),\, \text{anchor.plusMonths}(k+1).\text{minusDays}(1)]$$

### Pro-Rated Rent Calculation Formula (Mid-Cycle Departure):
When a resident checks out on a `checkOutDate` that falls **inside an active cycle** $[\text{cycleStart}, \text{cycleEnd}]$:
1. **Total Days in Billing Cycle**:
   $$\text{daysInCycle} = \text{ChronoUnit.DAYS.between}(\text{cycleStart}, \text{cycleEnd}) + 1$$
   *(Note: Accurately reflects calendar months — 28, 29, 30, or 31 days).*
2. **Daily Pro-Rated Rate**:
   $$\text{proRatedDailyRate} = \frac{\text{monthlyRent}}{\text{daysInCycle}}$$
3. **Actual Days Stayed in Current Cycle**:
   $$\text{stayedDaysInCycle} = \max\Big(1,\, \text{ChronoUnit.DAYS.between}(\text{cycleStart}, \text{checkOutDate}) + 1\Big)$$
4. **Pro-Rated Rent Charge**:
   $$\text{proRatedRent} = \text{round}\Big(\text{stayedDaysInCycle} \times \text{proRatedDailyRate},\, 2\Big)$$
5. **Unused Days**:
   $$\text{unusedDays} = \max(0,\, \text{daysInCycle} - \text{stayedDaysInCycle})$$

> **Important Architecture Constraint**:
> - The automated background job [`RentChargeGenerationJob`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/scheduler/RentChargeGenerationJob.java) and regular customer listings in `Customers.tsx` **remain untouched**. They continue to show full monthly charges for active residents.
> - The pro-rated calculation is dynamically evaluated and presented exclusively inside the **Checkout & Settlement Preview/Modal**.

## 3. Database Entities Strategy & Charge Reconciliation

When `checkOutDate` is confirmed by the receptionist, the backend reconciles charges in [`ChargeRepository`](file:///d:/resource/Projects/Hostel%20Management/aavas/src/main/java/com/atithi/aavas/repositories/ChargeRepository.java):

```
 Timeline View of Monthly Charges Reconciliation:
 ─────────────────────────────────────────────────────────────────────────────
 [ Past Full Cycles ]       [ Exit Cycle: Oct 1 - Oct 31 ]       [ Future Cycles ]
 Sep 1 ──────── Sep 30       Oct 1 ─────── Oct 12 ─────── Oct 31   Nov 1 ────────
   ✓ Full Month Rent           Pro-rated   │   Unused (19d)       ✗ Cancel / Delete
     Unchanged                 (12 days)   │   Cancel/Adjust
 ─────────────────────────────────────────────────────────────────────────────
```

### 1. Past Closed Cycles (`periodEnd < checkOutDate`):
- All charges for completed cycles remain completely unchanged.

### 2. Exit Cycle (`periodStart <= checkOutDate <= periodEnd`):
- **Scenario A: Full Charge Already Exists (Generated by Cron)**:
  - Existing charge amount = `monthlyRent` (e.g. ₹6,000).
  - Let `paidAmount = paymentAllocationRepository.sumAllocatedAmountByChargeId(charge.getId())`.
  - **Adjustment**:
    - Update `charge.setAmount(proRatedRent)` (e.g. ₹2,322.58).
    - Update `charge.setPeriodEnd(checkOutDate)`.
    - Update `charge.setNotes("Pro-rated monthly rent for " + stayedDaysInCycle + "/" + daysInCycle + " days (" + periodStart + " to " + checkOutDate + ")")`.
    - If `paidAmount >= proRatedRent`: Mark `charge.setStatus(ChargeStatus.PAID)`.
    - If `0 < paidAmount < proRatedRent`: Mark `charge.setStatus(ChargeStatus.PARTIAL)`.
    - If `paidAmount == 0`: Mark `charge.setStatus(ChargeStatus.OPEN)`.
- **Scenario B: Charge Not Yet Generated for Exit Cycle**:
  - Create new `Charge` with `chargeType = ChargeType.MONTHLY_RENT`, `periodStart = cycleStart`, `periodEnd = checkOutDate`, `amount = proRatedRent`, `status = OPEN`.

### 3. Future Speculative Charges (`periodStart > checkOutDate`):
- If checkout is backdated (e.g. resident left on Sep 25, updated on Oct 2):
  - Find all `MONTHLY_RENT` charges where `periodStart > checkOutDate`.
  - If unallocated (`status = OPEN`), **delete them** from `chargeRepository`.

## 4. Security Deposit Settlement & Refund Logic

Monthly residents almost universally have a `SECURITY_DEPOSIT` recorded at registration.

### Deposit Ledger Tracking:
- **Deposit Required**: `terms.getSecurityDepositRequired()`
- **Deposit Paid**:
  $$\text{depositPaid} = \text{paymentAllocationRepository.sumAllocatedAmountByCustomerIdAndChargeType}(\text{hostelId}, \text{customerId}, \text{SECURITY\_DEPOSIT})$$

### Deductions at Checkout (Damages / Room Cleaning / Notice Penalty):
- In the checkout modal, the receptionist can input:
  - `deductionAmount`: e.g. ₹500
  - `deductionReason`: e.g. "Room deep cleaning & broken window latch"
- If `deductionAmount > 0`:
  - Create a `Charge` with `chargeType = ChargeType.MAINTENANCE` (or damage charge), or deduct directly from refundable deposit.
- **Net Refundable Security Deposit**:
  $$\text{refundableDeposit} = \max(0,\, \text{depositPaid} - \text{deductionAmount})$$

### Net Settlement Equation:
Let $\text{OutstandingRentDues}$ be the remaining unpaid rent across all cycles (including pro-rated exit cycle):
$$\text{Net Settlement Balance} = \text{OutstandingRentDues} - \text{refundableDeposit}$$

Three clear operational outcomes:
1. **Outcome 1: $\text{Net Settlement Balance} > 0$ (Guest Owes Hostel)**:
   - Example: Unpaid rent ₹4,500, Refundable deposit ₹2,000 $\rightarrow$ Net Payable by Guest = ₹2,500.
   - Action: Guest pays ₹2,500 $\rightarrow$ Payment recorded $\rightarrow$ Bed vacated.
2. **Outcome 2: $\text{Net Settlement Balance} < 0$ (Hostel Owes Refund to Guest)**:
   - Example: All rent paid ₹0 due, Refundable deposit ₹5,000 $\rightarrow$ Net Refund to Guest = ₹5,000.
   - Action: Receptionist returns ₹5,000 via Cash / UPI / Bank Transfer $\rightarrow$ Bed vacated.
3. **Outcome 3: $\text{Net Settlement Balance} == 0$ (Clear Settlement)**:
   - Example: Unpaid rent ₹3,000, Refundable deposit ₹3,000 $\rightarrow$ Net = ₹0.
   - Action: Directly vacate bed with single confirmation.

## 6. Implementation Steps (Monthly Checkout)

### Phase 1: Backend (`aavas`)
1. **Create Preview & Settlement DTOs**:
   - `MonthlyCheckoutPreviewResponse`:
     ```java
     public record MonthlyCheckoutPreviewResponse(
         Long allocationId,
         Long customerId,
         String customerName,
         String roomNumber,
         String bedNumber,
         LocalDate checkInDate,

         // Cycle details
     ```

2. **Unified `EndRoomAllocationRequest` DTO**:
   ```java
   public record EndRoomAllocationRequest(
       @NotNull LocalDate checkOutDate,
       BigDecimal depositDeduction,       // Optional: damages/cleaning deductions
       String depositDeductionReason,     // Optional: reason for deduction
       SettlementPaymentRequest payment,  // If guest owes net balance
       RefundRequest refund               // If hostel refunds guest
   ) {
       public record SettlementPaymentRequest(
           @NotNull BigDecimal amount,
           @NotNull PaymentMethod paymentMethod,
           String transactionReference,
           String notes
       ) {}

       public record RefundRequest(
           @NotNull BigDecimal amount,
           @NotNull PaymentMethod paymentMethod,
           String transactionReference,
           String notes
       ) {}
   }
   ```

3. **New Preview API**:
   - `GET /api/v1/room-allocation/{id}/checkout-preview?checkOutDate=YYYY-MM-DD`
   - Detects `billingMode` from `AllocationFinancialTerms`:
     - If `DAILY`: computes daily stay days and daily tariff.
     - If `MONTHLY`: computes cycle breakdown, pro-rated rent, deposit paid, and net settlement preview.
4. **Enhanced `endAllocation` in `RoomAllocationServiceImpl`**:
   - For `billingMode == MONTHLY`:
     1. Reconcile exit cycle charge (adjust amount to `proRatedRent` and `periodEnd` to `checkOutDate`, or create if missing).
     2. Delete speculative unallocated charges where `periodStart > checkOutDate`.
     3. If `depositDeduction > 0`: record deduction charge or adjust deposit allocation.
     4. If `payment` provided: record `Payment` entity and allocate to outstanding charges oldest-first.
     5. If `refund` provided: record refund transaction / notes.
     6. Set `allocation.setCheckOutDate(checkOutDate)` and `allocation.setStatus(AllocationStatus.ENDED)`.
     7. Decrement room occupied count and update room status (`VACANT` or `PARTIALLY_FILLED`).

2. **Build `MonthlyCheckoutModal.tsx`**:
   - Reusable modal component adhering to the project's styling tokens (Tailwind/Vanilla CSS, Lucide icons, responsive layout).
   - Real-time debounced date selection triggering preview updates.

## 7. Comparison Matrix: Daily vs Monthly Checkout

| Feature / Behavior | Daily Room Checkout (`DAILY`) | Monthly Room Checkout (`MONTHLY`) |
| :--- | :--- | :--- |
| **Billing Frequency** | 1 charge per calendar day (`DAILY_RENT`) | 1 charge per monthly cycle (`MONTHLY_RENT`) |
| **Rate Basis** | Fixed `dailyRate` (e.g. ₹300/day) | `monthlyRent` (e.g. ₹6,000/month) |
| **Pro-Ration Rule** | Sum of days stayed $\times$ daily rate | Mid-cycle pro-ration: $\text{daysStayed} \times (\text{monthlyRent} / \text{daysInCycle})$ |
| **Excess / Future Charges** | Delete unallocated daily charges where `date > checkOutDate` | Adjust current cycle charge down to pro-rated amount; delete unallocated future month charges |
| **Security Deposit** | Usually zero or nominal | Substantial (e.g. 1 month rent); requires deduction + refund handling |
| **Settlement Direction** | Usually guest pays remaining daily dues | Can be **Pay Due** OR **Refund Deposit to Guest** |
| **Modal UI Location** | Triggered from `DailyRooms.tsx` ("Check-out & Vacate") | Triggered from `Customers.tsx` ("Exit" action) |
| **Background Cron Impact** | None (regular daily cron untouched) | None (regular monthly cron untouched) |

## 8. Common Ground & Unified Architecture (For Consolidated Implementation)

Both Daily and Monthly checkout share the following unified architectural backbone:
1. **Unified Endpoint**:
   `POST /api/v1/room-allocation/{id}/end`
   Accepts unified `EndRoomAllocationRequest`.
2. **Unified Preview Endpoint**:
   `GET /api/v1/room-allocation/{id}/checkout-preview?checkOutDate=YYYY-MM-DD`
   Returns the appropriate response structure based on the allocation's `billingMode`.
3. **Shared Core Actions**:
   - Room occupancy decrement (`roomRepository.decrementOccupancy(...)`).
   - Room status transition (`VACANT` / `PARTIALLY_FILLED`).
   - Oldest-first payment allocation via `PaymentAllocationService`.
   - Deletion of unallocated speculative future charges.
   - Allocation status update to `ENDED`.
